# Аналіз технічного завдання проєкту «Student Assistant»

**Освітня компонента:** «Кросплатформне програмування»\
**Спеціальність:** 122 «Комп'ютерні науки»\
**Практична робота:** № 4\
**Документ-основа:** технічне завдання на розробку наскрізного
навчального проєкту «Student Assistant»

## 1. Призначення та мета проєкту

«Student Assistant» - це навчальний кросплатформний гетерогенний
застосунок-планувальник завдань для студента. Він призначений для
керування навчальними завданнями: додавання, перегляду, редагування,
видалення, позначення виконаними та визначення їхнього пріоритету.

Функціональна мета проєкту - забезпечити єдиний узгоджений спосіб
керування навчальними завданнями з різних платформ та через різні форми
інтерфейсу.

Навчальна мета полягає в отриманні практичного досвіду створення системи
з кількох незалежних клієнтів, які працюють зі спільним форматом даних,
а також у використанні Git, GitHub та різних підходів до кросплатформної
розробки.

## 2. Основні вимоги до системи

### 2.1. Архітектурні вимоги

Система повинна складатися з чотирьох незалежних клієнтських модулів:

1.  **Веб-клієнт (React)** - вебінтерфейс для роботи із завданнями.
2.  **Десктопний контейнер (Electron або NW.js)** - оболонка для
    вебінтерфейсу.
3.  **Нативний десктопний клієнт (C++ / Qt)** - окремий нативний
    застосунок.
4.  **Аналітичний модуль (Python / Flet)** - модуль для відображення
    та аналізу даних.

Усі модулі повинні бути незалежно розгортуваними та не повинні мати
прямих залежностей один від одного. Обмін даними між ними здійснюється
через спільний файл `data/tasks.json`, розташований у корені
репозиторію.

### 2.2. Функціональні вимоги

Мінімальний набір функцій кожного клієнта:

-   перегляд переліку навчальних завдань;
-   додавання нового завдання із зазначенням назви, дедлайну та
    пріоритету;
-   позначення завдання виконаним або невиконаним;
-   редагування завдання;
-   видалення завдання.

Бажаною, але не обов'язковою для кожного окремого клієнта, є можливість
фільтрації або сортування за станом виконання чи пріоритетом.

### 2.3. Формат даних

Для всіх клієнтів використовується єдиний файл `data/tasks.json`. Кожен
запис є JSON-об'єктом із такими полями:

  Поле          Тип        Призначення
  ------------- ---------- ---------------------------------------
  `id`          числовий   Унікальний ідентифікатор завдання
  `title`       рядок      Назва завдання
  `completed`   логічний   Стан виконання: `true` або `false`
  `dueDate`     рядок      Дедлайн у форматі `YYYY-MM-DD`
  `priority`    рядок      Пріоритет: `low`, `medium` або `high`

Приклад запису:

``` json
[
  {
    "id": 1,
    "title": "Підготувати практичну роботу",
    "completed": false,
    "dueDate": "2026-11-10",
    "priority": "high"
  },
  {
    "id": 2,
    "title": "Повторити лекційний матеріал",
    "completed": true,
    "dueDate": "2026-11-12",
    "priority": "medium"
  }
]
```

Жоден клієнт не повинен самовільно змінювати назви, типи або призначення
полів. Спільний формат має бути описаний у `README.md`.

## 3. Нефункціональні вимоги

-   Сукупність клієнтських модулів повинна забезпечувати роботу
    щонайменше у Windows, macOS та Linux.
-   Кожен модуль має використовувати архітектурний підхід
    кросплатформності, передбачений відповідною темою курсу.
-   Розробка та історія змін ведуться через Git і GitHub.
-   Для кожної окремої задачі створюється окрема гілка.
-   Зміни передаються через Pull Request та проходять рецензування коду.
-   Репозиторій повинен містити `README.md` з описом призначення
    проєкту, архітектури, технологій та структури директорій.

зафіксована технічним завданням. Її можна уточнювати під час розробки за
умови збереження спільного файлу даних та незалежності клієнтів.

## 6. Критерії перевірки та приймання

Під час перевірки проєкту доцільно контролювати:

1.  Наявність чотирьох передбачених клієнтських модулів.
2.  Незалежність модулів один від одного.
3.  Використання спільного файлу `data/tasks.json`.
4.  Відповідність JSON-записів установленій структурі.
5.  Реалізацію основних операцій із завданнями.
6.  Коректне читання та запис даних.
7.  Дотримання правил роботи з Git і GitHub.
8.  Наявність та повноту `README.md`.
9.  Можливість запуску компонентів на цільових операційних системах.

Згідно з технічним завданням, проміжний контроль виконується на
практичних роботах, а підсумкове приймання передбачає комплексне
інтеграційне тестування, презентацію та захист проєкту на заняттях №
44-45.

## 7. Питання, які потрібно уточнити під час подальшої розробки

Технічне завдання визначає основну архітектуру та формат обміну даними,
але не деталізує деякі аспекти реалізації. Перед інтеграцією бажано
узгодити:

-   як клієнти визначатимуть шлях до спільного файлу `data/tasks.json` у
    різних середовищах запуску;
-   як уникати втрати змін, якщо два клієнти одночасно записують дані у
    файл;
-   як оброблятимуться відсутній, порожній або пошкоджений JSON-файл;
-   як формуватимуться унікальні числові значення `id`;
-   чи потрібне підтвердження перед видаленням завдання;
-   які саме показники та діаграми повинен відображати аналітичний
    модуль.

Ці питання є рекомендаціями для уточнення під час проєктування. Вони не
змінюють вимог до спільного формату даних, установлених технічним
завданням.

## 8. Висновок

У результаті аналізу встановлено, що «Student Assistant» має бути
гетерогенною кросплатформною системою, яка складається з чотирьох
незалежних клієнтів: React, Electron або NW.js, C++/Qt та Python/Flet.
Основою їхньої взаємодії є спільний файл `data/tasks.json` з узгодженою
структурою записів.

Для успішної реалізації необхідно забезпечити однакове трактування полів
JSON у всіх модулях, реалізувати основні операції керування завданнями,
дотримуватися вимог кросплатформності та вести розробку через Git і
GitHub. Аналіз вимог зафіксовано в цьому документі `docs/tz-notes.md`,
який може бути використаний як основа для подальшої деталізації
специфікації.
